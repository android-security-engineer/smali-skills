# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

smali/baksmali is an assembler/disassembler for the dex format used by Dalvik (Android's VM). The
syntax is loosely based on Jasmin's/dedexer's. The repo also ships `dexlib2`, the underlying library
for reading/modifying/writing dex files, which is the most reusable and most-edited part of the codebase.

## Build & test

Gradle multi-module project (Java 8 source/target). Use the wrapper.

```bash
./gradlew build                       # compile, run all tests, build fat jars
./gradlew :dexlib2:test               # test a single module
./gradlew :baksmali:test --tests '*DisassemblyTest'   # single test class (Gradle test filter)
./gradlew :baksmali:fb                # baksmali "fast build" — build but skip its tests + javadoc
```

After `build`, runnable fat jars are at `smali/build/libs/smali.jar` and
`baksmali/build/libs/baksmali.jar` (symlinks created on non-Windows). The `scripts/smali` and
`scripts/baksmali` wrappers invoke `java -jar` on these. Main classes are `org.jf.smali.Main` and
`org.jf.baksmali.Main` (both jcommander-based CLIs with subcommands).

Version is derived in `build.gradle` from the git HEAD short hash (e.g. `2.5.2-<hash>` or
`-dirty`); `release` builds drop the suffix and bump the jcommander version.

## Module layout & dependency direction

`settings.gradle` includes: `util`, `dexlib2`, `baksmali`, `smali`, `dexlib2:accessorTestGenerator`.

- **dexlib2** — core library, no dependency on the others. Everything else depends on it.
- **util** — shared helpers; depends on dexlib2.
- **smali** — the assembler; `api project(':dexlib2')`, depends on util.
- **baksmali** — the disassembler; depends on dexlib2 + util, and on `:smali` *for tests* (round-trip).

`smali-integration-tests/` is a standalone tree, **not** part of `settings.gradle`.

## Generated code — do not hand-edit, and regenerate when grammars change

Several sources are generated at build time from grammar/spec files. Edit the input, not the output.

- **smali assembler** is ANTLR3 + JFlex. Inputs live in `smali/src/main/`:
  - `jflex/smaliLexer.jflex` → lexer
  - `antlr/smaliParser.g` → parser (token stream → AST)
  - `antlr/smaliTreeWalker.g` → tree walker (AST → dexlib2 builder objects)
  The `generateGrammarSource` / jflex Gradle tasks run automatically during `build`. The assembly
  pipeline is: lexer → parser → tree walker → dexlib2 writer.
- **dexlib2 `SyntheticAccessorFSM.java`** is generated by **ragel** and is *not* regenerated
  automatically. After editing `dexlib2/src/main/ragel/SyntheticAccessorFSM.rl`, run `./gradlew ragel`
  (requires the `ragel` binary on PATH) and commit the generated `.java`.
- **dexlib2 accessor test fixtures** — `generateAccessorTestSource` (via the `accessorTestGenerator`
  subproject) emits `AccessorTypes.java`; `generateAccessorTestDex` (run manually) regenerates
  `src/test/resources/accessorTest.dex` using `dx`.

## dexlib2 architecture (the part you'll most often touch)

dexlib2 models a dex file through layered representations under `org.jf.dexlib2`:

- **`iface/`** — read-only interfaces (`DexFile`, `ClassDef`, `Method`, `Instruction`, references,
  encoded values, debug items). The common currency between reading and writing.
- **`dexbacked/`** — lazy, zero-copy implementations that read directly from the raw dex byte buffer
  (`DexBackedDexFile`, `DexBackedClassDef`, …). Entry point for parsing is `DexFileFactory`, which
  also handles odex/oat (`OatFile`, `DexBackedOdexFile`) and zip containers (`ZipDexContainer`).
- **`immutable/`** — fully-materialized, in-memory implementations of the `iface` types; use these
  when you need to hold/modify a dex independent of its backing bytes.
- **`builder/`** — mutable method-body construction (`MutableMethodImplementation`, builder
  instructions, labels, try/catch) — what the smali tree walker targets.
- **`writer/`** — serializes `iface` objects back to a dex. `DexWriter` orchestrates the per-section
  writers; `writer/pool/` and `writer/builder/` are two strategies for interning/ordering pool items.
- **`rewriter/`** — transform a dex by overriding `Rewriter`s (rename types, remap references, etc.).
- **`analysis/`** — deodexing & type inference (`MethodAnalyzer`, `ClassPath`, register type lattice);
  needed to resolve odexed instructions back to concrete invokes/field accesses.

`Opcode.java` / `Opcodes.java` and `VersionMap.java` encode which opcodes/format exist per dex/API
version — when adding bytecode or version support, these plus the format enums in `iface/instruction`
are the touch points.

baksmali's disassembly output is produced by the `Adaptors/` classes (one per dex element) plus
`formatter/`, which write smali text; `org.jf.baksmali` orchestrates the multi-threaded dump.

## Tests

JUnit 4 (+ Mockito in dexlib2). Many baksmali/smali tests are **round-trip**: a `.smali` or `.dex`
fixture under `src/test/resources/<TestName>/` or `src/test/smali/` is assembled and/or disassembled
and compared. When adding such a test, add the fixture directory alongside a `*Test.java` that points
at it (see `baksmali/src/test/java/org/jf/baksmali/` for the pattern). dexlib2 ships pre-built
`.dex`/`.odex` binaries as test resources.
